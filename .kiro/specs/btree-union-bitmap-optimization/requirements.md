# B-Tree Union Bitmap 优化需求文档

## 简介

当前的 range query 性能存在瓶颈：需要遍历范围内的所有 keys，逐个合并 bitmap。本优化通过在 B-Tree 的非叶子节点存储子树的 bitmap 并集，大幅提升 range query 性能。

## 术语表

- **B-Tree**：平衡树索引结构，用于存储倒排索引
- **RoaringBitmap**：压缩的位图数据结构，用于存储文档 ID 列表
- **Union Bitmap**：多个 bitmap 的并集
- **Range Query**：范围查询，例如 `age BETWEEN 18 AND 65`
- **非叶子节点**：B-Tree 中的内部节点，包含指向子节点的指针
- **叶子节点**：B-Tree 中的最底层节点，存储实际的 key-value 数据

## 需求

### 需求 1：性能优化

**用户故事**：作为数据库用户，我希望范围查询（如 `age BETWEEN 18 AND 65`）能够快速返回结果，这样我的应用响应时间更短。

#### 验收标准

1. **当执行范围查询时**，系统应该利用 B-Tree 非叶子节点的 union bitmap 来加速查询
2. **当范围覆盖整个子树时**，系统应该直接使用该子树的 union bitmap，而不是遍历所有叶子节点
3. **当范围查询覆盖 1000 个 keys 时**，查询时间应该从 O(n) 降低到 O(log n)
4. **当范围查询返回结果时**，结果的正确性应该与优化前完全一致

### 需求 2：构建时生成 Union Bitmap

**用户故事**：作为数据库管理员，我希望在构建索引时自动生成 union bitmap，这样我不需要额外的操作就能获得性能优化。

#### 验收标准

1. **当构建索引时**，系统应该自动计算所有非叶子节点的 union bitmap
2. **当持久化索引时**，系统应该将 union bitmap 写入磁盘
3. **当构建完成后**，索引文件应该包含完整的 union bitmap 数据
4. **当构建失败时**，系统应该能够清理部分写入的数据，不留下损坏的索引

### 需求 3：存储效率

**用户故事**：作为系统运维人员，我希望 union bitmap 的存储开销可控，不会导致索引文件大小显著增加。

#### 验收标准

1. **当存储 union bitmap 时**，系统应该使用 RoaringBitmap 的压缩格式
2. **当 union bitmap 与子节点 bitmaps 的并集相同时**，系统应该避免重复存储
3. **当索引文件大小增加时**，增加幅度应该小于 20%
4. **当读取索引时**，系统应该能够正确解析包含 union bitmap 的索引文件

### 需求 4：向后兼容

**用户故事**：作为数据库升级用户，我希望新版本能够读取旧版本的索引文件，这样我不需要重建所有索引。

#### 验收标准

1. **当读取旧版本索引文件时**，系统应该能够正常工作（降级到逐个合并 bitmap）
2. **当写入新版本索引文件时**，系统应该包含版本标识
3. **当检测到旧版本索引时**，系统应该记录日志提示用户可以重建索引以获得更好性能
4. **当新旧版本混合使用时**，系统应该能够正确处理两种格式的索引

### 需求 5：内存版本不修改

**说明**：内存版本的 B-Tree 不做修改，原因如下：

1. **内存版本性能已经很好**：内存操作本身就很快，bitmap 合并开销相对较小
2. **保持 mem_btree 的通用性**：mem_btree 是通用库，不应该耦合 bitmap 逻辑
3. **简化实现**：只优化磁盘版本，降低复杂度和风险

#### 验收标准

1. **当使用内存 B-Tree 时**，系统应该使用原始的 range query 算法
2. **当执行 range query 时**，内存版本和磁盘版本的结果应该完全一致
3. **当内存 B-Tree 转换为磁盘格式时**，应该生成包含 union bitmap 的索引文件
4. **当从磁盘加载到内存时**，union bitmap 信息可以被忽略（内存版本不使用）

## 性能目标

### 当前性能（优化前）

```
场景：age BETWEEN 18 AND 65
- Keys 数量：1000
- 每个 key 的 bitmap 大小：平均 1000 个文档
- 操作：1000 次 bitmap 合并
- 时间复杂度：O(n)，其中 n = keys 数量
- 预估耗时：~100ms
```

### 目标性能（优化后）

```
场景：age BETWEEN 18 AND 65
- Keys 数量：1000
- B-Tree 高度：3
- 操作：访问 ~10 个非叶子节点，直接获取 union bitmap
- 时间复杂度：O(log n)
- 预估耗时：~10ms
- 性能提升：10x
```

## 非功能需求

### 可靠性

1. 系统应该在节点更新失败时能够回滚
2. 系统应该在崩溃后能够恢复索引的一致性
3. Union bitmap 的计算应该是确定性的（相同输入产生相同输出）

### 可维护性

1. 代码应该清晰地分离 union bitmap 的维护逻辑
2. 应该提供调试工具来验证 union bitmap 的正确性
3. 应该有详细的文档说明 union bitmap 的工作原理

### 可测试性

1. 应该有单元测试覆盖 union bitmap 的计算逻辑
2. 应该有集成测试验证 range query 的正确性
3. 应该有性能测试对比优化前后的性能差异

## 约束条件

1. **只优化 Disk 版本**：本次优化只针对磁盘版本的 B-Tree（TreeReader/TreeWriter），内存版本（BTree）不修改
2. **不修改 mem_btree 核心逻辑**：mem_btree 是通用库，保持其通用性，不耦合 bitmap 逻辑
3. **在上层实现优化**：union bitmap 的计算和存储在 field_store 层实现，利用 mem_btree 提供的接口
4. **保持 API 不变**：对外的 API（IndexReader::range）不应该改变
5. **渐进式实现**：可以分阶段实现，先支持写入，再支持读取
6. **性能不能退化**：在任何情况下，性能都不应该比优化前差

## 风险评估

### 高风险

1. **数据损坏**：如果 union bitmap 计算错误，可能导致查询结果不正确
2. **性能退化**：如果实现不当，可能导致性能反而下降

### 中风险

1. **存储开销**：union bitmap 可能显著增加索引文件大小
2. **兼容性问题**：新旧版本的索引格式不兼容

### 低风险

1. **实现复杂度**：代码复杂度增加，维护成本上升
2. **测试覆盖**：需要大量测试用例来验证正确性

## 成功标准

1. ✅ Range query 性能提升 5x 以上
2. ✅ 所有现有测试用例通过
3. ✅ 新增测试覆盖率 > 90%
4. ✅ 索引文件大小增加 < 20%
5. ✅ 能够读取旧版本索引文件
6. ✅ 代码审查通过
7. ✅ 性能测试通过
